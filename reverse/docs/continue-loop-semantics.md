# Two continue placements changed finite scans into cycles

The six nonstacking container repairs were followed by a review of the eight remaining `while(true)` forms in Main. Two more loops lost their original increment/termination control flow: `SetKeyPanel.closeOk` and `Achievement.getIddo`. They are separate from the fifteen NaN guards and were not found by the negated-comparison census: their original bound branches use `iflt`.

`SetKeyPanel.closeOk` checks both players' sixteen key assignments when player2 exists. The original returns false at the first −1 key, advances after valid pairs and returns true after all16 pairs. The recovered loop's `continue` bypassed the increment while inside the bound, so a valid first pair caused a repeated unchanged state. The repaired source bounds the loop, retains the two rejection checks, increments after a valid pair and returns true after exhaustion. The single-player branch was not changed.

In `Achievement.getIddo`, the multiple-map branch originally scans every configured map. A matching map/star that satisfies `isRy` or `_tg` calls `dbNum(param2,param1)`; otherwise the index advances, and exhaustion returns false. The recovered `continue` skipped the increment unless returning, so an unmatched or ineligible first entry could cycle. The repair restores a bounded scan and false on exhaustion. It does not alter the single-map branch or the implementation of `dbNum`.

`reverse/tools/audit_continue_loops.py` executes the actual original and old928e P-code under an explicit small fixture model. Eighteen fixtures cover valid/invalid player keys, multiple-map matching positions, stars and eligibility. Original paths return in all18; old928e cycles in11 (4 key cases,7 achievement cases). Unknown executed opcodes or unlisted getters are rejected. `dbNum` is a fixture stub, so these results establish branch/call selection, not achievement side effects or the AVM behavior of arbitrary objects. Full method P-code and fixture results are retained in `reverse/manifests/continue-loops.json`.

Root authorized and the CRLF-aware candidate passed `git apply --check` before application. `reverse/manifests/main-continue-repairs.json` records the two methods' original ABC body provenance, source/method before-and-after hashes and applied patch hash. Together with `main-semantic-repairs.json`, Main has24 repaired methods across8 files. Fresh compilation validation is recorded separately, never by rewriting historical application receipts.

The six other remaining `while(true)` forms were reviewed without another repair: four JSON parser/tokenizer methods, `EquipSlot.testAllEquip` and `Achievement.getNumByType`. `reverse/manifests/remaining-while-loop-review.json` records their local control-flow reasoning and three JSON helpers. This is a scoped review of the suspicious forms, not a proof of full parser or Main equivalence.

Some external SWFs contain older copies with extra `trace` or validation calls. They require their own original method proof and a local repair preserving those calls; replacing every identically named method with Main's body is not valid. Parent-domain resolution can mask a defective external copy in a particular game session and does not remove that obligation.

The subsequent Main2c0b888c0b16 compilation passed the affected actual-P-code fixtures in `manifests/main-semantic-repairs-validation-2c0b888c0b16.json` (172 container and18 continue fixtures total), plus the other repaired branch/int32 checks. This is fresh compiled-code evidence; runtime game behavior remains a separate validation layer.
